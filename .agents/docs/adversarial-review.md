# Adversarial Review Notes

This record captures the adversarial checks that matter before treating `css-fuzzer` output as useful parser evidence. The goal is to make failure modes explicit enough that a future change can re-run the right gates instead of trusting a green unit-test suite alone.

## Review Scope

- Differential parser oracle: postcss, Prettier CSS parser, lightningcss, and the local `oxc-css-parser` driver.
- Spec sourcing: live CSSWG index fetch, selected spec downloads, example extraction, corpus freshness, and generator reachability.
- Finding lifecycle: generation, parser replay, minimization, deduplication, report writing, and promotion into the companion cases repository.
- Case repository gate: README human triage table, sidecar notes, parser matrix replay, current-interest checks, and minimizer stability.
- Metamorphic oracles: lightningcss transformed output and Prettier formatted output.

## Failure Modes And Current Defenses

| Failure mode                                                               | Why it would be bad                                                               | Current defense                                                                                                                       | Verification                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A parser adapter is missing but the campaign still runs.                   | Findings would be biased because one parser silently disappeared.                 | Evidence-producing commands smoke-test all required adapters before running.                                                          | `vp test tests/adapterAvailability.test.ts`; `vp test tests/adapters.integration.test.ts`; `vp run build:oxc-driver` before full gates.                                                                                                                             |
| OXC recoverable errors are treated as normal acceptance.                   | Recoverable parser errors would disappear from the disagreement signal.           | OXC reports `accepted_with_errors` with the first recoverable error message, and fingerprints preserve that status.                   | `vp test tests/adapters.integration.test.ts`; `vp test tests/differential.test.ts`.                                                                                                                                                                                 |
| A malformed JS worker response becomes parser evidence.                    | Infrastructure corruption could masquerade as parser behavior.                    | Adapter protocol parsing validates statuses and restarts malformed persistent workers.                                                | `vp test tests/adapterProtocol.test.ts`.                                                                                                                                                                                                                            |
| Spec corpus goes stale or was generated from a partial fetch.              | The generator could stop covering current CSS syntax while still producing cases. | Corpus manifests record selected/downloaded/failed specs and timestamps; verification requires fresh matching corpus and index files. | `vp run fetch-specs -- --download`; `vp run verify-spec-corpus`.                                                                                                                                                                                                    |
| Required specs are present in metadata but unreachable in generated cases. | Coverage would exist only on paper.                                               | Generator coverage verification samples a deterministic window and checks required spec refs and tag families.                        | `vp run verify-generator-coverage -- --require-selected-specs`.                                                                                                                                                                                                     |
| Spec examples contain prose, HTML, or JavaScript fragments.                | Non-CSS input would produce noisy parser disagreements.                           | The fetcher and loader normalize and filter examples before they become seeds.                                                        | `vp test tests/specCorpus.test.ts`; `vp test tests/fetchCsswg.test.ts`.                                                                                                                                                                                             |
| Minimization changes the underlying parser disagreement.                   | A small repro would no longer prove the original finding.                         | Minimized findings are replayed and must preserve interesting status fingerprints; known issue families must also be preserved.       | `vp test tests/minimizedFinding.test.ts`; `vp test tests/differential.test.ts`; `vp run verify-cases -- --check-minimized`.                                                                                                                                         |
| Different raw findings reduce to the same final report.                    | Campaign output would overstate issue count.                                      | Deduplication runs before and after minimization using normalized source plus parser-result fingerprint.                              | `vp test tests/findingDedup.test.ts`.                                                                                                                                                                                                                               |
| Reports or summaries are overwritten by a later run.                       | Evidence for a campaign could be silently lost.                                   | Report and summary files use exclusive writes.                                                                                        | `vp test tests/report.test.ts`; campaign runs into a fresh `findings/<name>` directory.                                                                                                                                                                             |
| Known cases suppress new unrelated findings too broadly.                   | The fuzzer would miss fresh issues because known-family matching is too loose.    | Known-dir matching is exact by default; family suppressions are narrow and documented in `fuzzer-design.md`.                          | `vp test tests/findingArchive.test.ts`; `vp run verify-findings-known -- --findings-dir <dir> --known-dir <cases>`.                                                                                                                                                 |
| README becomes a stale or machine-hostile source of truth.                 | Human triage would drift from replayed parser facts.                              | README is only the human OXC triage index; exact parser evidence lives in sidecar notes and is replayed by `verify-cases`.            | `vp run verify-cases -- --dir <cases> --readme <README.md> --check-minimized`.                                                                                                                                                                                      |
| OXC-clean cases crowd the README.                                          | The top-level cases table stops being useful for OXC parser triage.               | `verify-cases` derives current OXC non-clean-accept cases from replay and rejects README links for OXC clean accepts.                 | `vp test tests/caseRepo.test.ts`; `vp run verify-cases -- --dir <cases> --readme <README.md>`.                                                                                                                                                                      |
| Sidecar notes contain empty context headings.                              | A case can look report-ready while omitting the actual spec or triage reasoning.  | Sidecar `Spec Context` or `Triage Note` sections must contain non-empty explanatory text.                                             | `vp test tests/caseRepo.test.ts`; `vp run verify-cases -- --dir <cases> --readme <README.md>`.                                                                                                                                                                      |
| Formatter output disagrees with the parser matrix.                         | The raw parser oracle can miss accepted-input/emitted-output bugs.                | Separate lightningcss and Prettier roundtrip oracles write minimized replayable reports.                                              | `vp run verify-lightning-roundtrip -- --known-dir ../css-parser-fuzzer-cases/cases --out findings/lightning-roundtrip --minimize`; `vp run verify-prettier-roundtrip -- --known-dir ../css-parser-fuzzer-cases/cases --out findings/prettier-roundtrip --minimize`. |

## Current Integrated Gate Set

Run this set before claiming a report-ready cases repository:

```sh
vp run verify-report-ready
```

`verify-report-ready` expands to the full gate set: `check`, `test`, `build`, OXC driver build, live spec fetch, spec corpus verification, selected-spec generator coverage, minimized cases verification, one minimized fuzz campaign, lightningcss and Prettier roundtrip oracles, and `verify-findings-known` for every output directory. It writes fresh ignored output under `findings/report-ready-<timestamp>/` by default. A zero-finding campaign is still evidence only when its summary is written and `verify-findings-known` passes.

## Residual Risks

- Differential fuzzing cannot prove that every CSS parser bug has been found. It can only provide campaign evidence under the current generator, corpus, parser versions, timeout, and known-case set.
- CSSWG drafts can change between corpus refreshes. Keep `fetch-specs -- --download` and `verify-spec-corpus` in the campaign preflight path.
- Sidecar context is still human-written. The verifier can require non-empty explanatory text and parser matrix consistency, but it cannot prove that a spec interpretation is correct.
- Known issue families must stay narrow. Add a family only when exact-source matching would clearly re-report the same root cause across harmless syntax variation.
