# Fuzzer Design Context

This project uses differential fuzzing as the first oracle because the CSS language has broad recovery behavior and no single JavaScript parser can be treated as the complete truth for all current CSS drafts.

The core generator is deterministic by seed. A failing seed must be replayable with the same TypeScript code, dependency versions, parser versions, syntax mode, and downloaded spec corpus revision.

Downloaded spec examples are both direct seeds and mutation seeds. The generator can pair them with generated rules or wrap nest-safe examples in `@layer`, `@media`, or `@supports`; top-level-only at-rules such as `@charset`, `@import`, and `@namespace` are not nested.

The fuzzer intentionally records `accepted_with_errors` separately from `accepted`. OXC exposes recoverable parser errors while still returning an AST; treating that as plain acceptance would hide disagreements that matter to formatters and parser consumers. The local OXC driver records the first recoverable error message, so fingerprints and case README entries can distinguish different recoverable-error families.

The JavaScript parser adapters distinguish syntax parse errors from internal parser exceptions. Expected CSS syntax errors are `rejected`; non-syntax API exceptions such as Prettier `TypeError`s are `crashed` so they remain hard failures.

The JavaScript parser adapters run through reusable worker processes, one per parser, so campaign runs do not pay a process spawn for every input. Use `vp run bench-adapters -- --iterations <n>` before and after changing adapter process models, timeout handling, or parser invocation details. It reports per-parser total and average latency plus status counts, giving campaign throughput work a concrete local baseline.

Parser child-process responses are treated as an untrusted protocol boundary. JS worker and OXC driver responses must contain one of the known parser statuses, and optional messages must have the expected shape; malformed responses are infrastructure crashes, not parser oracle facts. If a persistent JS worker returns malformed protocol output, the runner restarts that worker before the next parse so a corrupted stream cannot affect later cases.

Parser coverage is mandatory for default evidence-producing commands. `fuzz`, `replay`, `reduce`, and `verify-cases` run a basic CSS smoke parse through postcss, Prettier CSS, lightningcss, and OXC before doing work; unsupported or non-accepting adapters fail the command instead of being silently ignored.

The fuzzer is deliberately CSS-only. `--syntax` accepts only `css` because the current adapter matrix uses postcss's default CSS parser, Prettier's CSS parser, lightningcss CSS transforms, and the OXC CSS driver. Preprocessor syntaxes need their own adapter-mode work before they can produce trustworthy differential findings.

Raw fuzz inputs are not final bug reports. A case only becomes report-quality after the minimizer preserves the same parser-status disagreement on a smaller input and the parser versions are recorded.

Fuzz finding JSON records the run environment and campaign metadata next to the finding. The environment includes Node version, package manager, parser package versions, OXC checkout commit when available, and spec corpus metadata. The run metadata includes root seed, iteration count, syntax, timeout, minimization settings, output directory, known-dir, and spec corpus path. Keep `.css` outputs plain so they stay easy to replay by hand. Finding reports, `campaign-summary.json`, and `roundtrip-summary.json` are exclusive writes, so repeated runs into the same output directory fail on an existing case id or summary instead of silently overwriting evidence. Every `fuzz` campaign also writes `campaign-summary.json` with campaign-level counts, generated tag/spec-ref coverage, and finding output paths, including zero-finding runs where all interesting inputs were already known or duplicated inside the same run. Roundtrip commands with `--out` write `roundtrip-summary.json` with run metadata, generated/checked counts, skipped-input counts, known/duplicate skips, mismatch count, and written finding paths.

Downloaded CSSWG editor drafts are working inputs, not canonical checked-in truth. Keep the manifest and extracted examples reproducible, but avoid committing large raw HTML unless a human asks for a pinned snapshot. Campaign commands reject spec corpora older than the default 72 hour freshness window unless the caller intentionally raises `--max-spec-corpus-age-hours`; `verify-spec-corpus` also requires `examples.json` and `csswg-index.json` to have matching `fetchedAt` values so an old index cannot be mixed with a fresh example corpus.

Treat spec examples as untrusted input even after extraction. The loader normalizes examples when the corpus is read, and the generator runs the same normalization again before allowing a corpus chunk into weighted generation, so prose snippets that happen to contain CSS punctuation cannot bypass the fetch-time filters.

Run `vp run verify-generator-coverage` after changing generator weights, tags, spec seed references, or corpus normalization. It checks a deterministic seed window against required modern spec refs and the main generator tag families, proving that required syntax areas are reachable in actual generated cases rather than only present in the corpus metadata. Run `vp run verify-generator-coverage -- --require-selected-specs` before a full campaign; it uses a larger deterministic window and requires every currently selected CSSWG spec in the corpus manifest to appear in actual generated cases.

Use `vp run verify-lightning-roundtrip -- --known-dir ../css-parser-fuzzer-cases/cases --out findings/lightning-roundtrip --minimize` as a separate metamorphic oracle for lightningcss output. Cross-parser AST shape comparison is too noisy with the current adapter mix, but lightningcss transformed CSS should still be parseable by the same parser matrix when the original input was accepted; this gate catches accepted-input/emitted-output inconsistencies without changing the main differential status oracle, and `--known-dir` keeps already filed roundtrip cases from failing every future run. Unknown mismatches written with `--out` use the transformed CSS as the replayable `.css` file and preserve the original trigger case plus original parser results in JSON metadata. The same output directory also gets `roundtrip-summary.json`, including zero-mismatch or fully known runs. With `--minimize`, the written CSS is reduced while preserving the transformed-output parser fingerprint.

Use `vp run verify-prettier-roundtrip -- --known-dir ../css-parser-fuzzer-cases/cases --out findings/prettier-roundtrip --minimize` for the same kind of check against Prettier's CSS formatter. It intentionally skips raw inputs that are already interesting under the parser matrix, so known parser support gaps such as column-combinator handling do not get re-reported as formatter-output bugs. Unknown mismatches written with `--out` use the formatted CSS as the replayable `.css` file and preserve the original trigger case plus original parser results in JSON metadata. The same output directory also gets `roundtrip-summary.json`, including zero-mismatch or fully known runs. If Prettier's parser accepts an input but the formatter crashes before producing CSS, the report writes the original trigger CSS and records `prettier-css=crashed` with the formatter error message. With `--minimize`, the written CSS is reduced while preserving the formatted-output parser fingerprint or formatter crash message.

The runner deduplicates findings inside a campaign by normalized source plus supported parser status and the first line of each parser error message. It applies the check before minimization and again after minimization, so two different raw inputs that shrink to the same final case do not both get written. This only skips exact duplicate inputs; different CSS sources with the same parser message still surface unless a known issue family suppresses them.

The minimizer is not allowed to weaken evidence. After reduction, the runner replays the minimized source and only reports it if the final result is still interesting and preserves the original parser fingerprint; recognized known issue families must preserve the family as well. If the final replay check fails, report the original finding and warn instead of writing a misleading minimized case.

Use `vp run replay -- --dir <cases>` to regenerate parser matrices from saved `.css` files, and `vp run reduce -- --file <raw.css> --out <min.css>` to produce a readable structure-level reduction for a raw finding. Byte-level reduction is opt-in through `--byte-minimize` because it can preserve a parser fingerprint while making the CSS hard to read.

Before treating the companion cases repository as report-ready, run `vp run verify-cases -- --dir <cases> --readme <README.md> --check-minimized`. This keeps one sidecar `.md` note per `.css` case, no orphan sidecar notes, sidecar `css` reproduction blocks matching their `.css` files, required sidecar headings (`Minimal Reproduction`, `Parser Results`, and either `Spec Context` or `Triage Note`), complete sidecar parser result tables with error-message snippets for every non-accepted result, and sidecar parser matrix drift in one gate. The README is a human OXC triage index rather than the full evidence store: it must cover every current OXC non-clean-accept case, omit OXC clean-accept cases, keep unique README IDs matching linked case file basenames, keep High/Medium/Low priority grouping consistent with paths, and provide parser emoji summary rows with a separate parser-notes column. A case fails the minimization check only when a shorter candidate preserves the exact same parser-result fingerprint, and for recognized issue families also preserves that family. Byte-level minimization is useful as an adversarial diagnostic; the verifier prints exact candidate strings, but those candidates still need human review before replacing readable report cases.

Campaigns should run with `--known-dir ../css-parser-fuzzer-cases/cases` once a cases repository exists. The runner replays those cases first and skips matching normalized source plus parser-result fingerprints, so filed exact cases do not reappear while different source inputs with the same first-line parser message can still surface. Prettier roundtrip/archive commands also run the current Prettier formatter over known cases whose parser matrix is otherwise uninteresting, so archived formatter-crash cases can suppress future `prettier-format-crash` reports. Only cases that still replay as interesting under current parser versions, or still reproduce a formatter crash under the current Prettier version, become known fingerprints or known families; stale all-accepted cases should be reported by `verify-cases`, not silently used to suppress new campaign results.

Run `vp run verify-findings-known -- --findings-dir <campaign-output> --known-dir ../css-parser-fuzzer-cases/cases` after a campaign or roundtrip oracle writes report files. This gate reads finding JSON reports, ignores `campaign-summary.json` and `roundtrip-summary.json`, replays each report's CSS with the current parser adapters, and checks each current source/result matrix against the current cases repo with the same exact-source and issue-family matching used by fuzz campaigns. For `prettier-format-crash` reports, it also reruns the current Prettier formatter so fixed formatter crashes become stale instead of looking like current parser issues. A pass means the output directory has no currently reproducible unarchived findings; a failure lists the report files that still need to become minimized cases with README matrix rows and sidecar notes. Reports that no longer reproduce an interesting disagreement are listed as stale instead of blocking the gate. Minimized reports are replayed from their minimized source.

Known-dir matching is exact by default. The current family-level suppressions are `@property` initial-value validation where lightningcss rejects different value token kinds with the same parser-status shape, Selectors column-combinator findings where nesting changes lightningcss's error text for the same `||` root cause, Selectors reference-combinator findings where comments or selector lists change the surrounding source for `/for/`, generated marker pseudo-element chain findings, Shadow Parts multi-ident `::part()` findings, CSS Color 5 `@color-profile device-cmyk` recoverable OXC errors, `@scope` relative selector findings, `@scope ()` empty-root roundtrip findings, container query list findings where lightningcss rejects a comma-separated query list, container query `var()` threshold findings, name-only container query findings, the known column-combinator plus name-only container-query cross-product, anchored container query findings, CSS Link Parameters `url(... param(...))` findings, legacy `url(var(...))` BadUrl findings, nested `var()` reference findings, page slot pseudo findings, page `@slot` rule findings, page `@top` margin rule findings, scroll-driven keyframe range findings, late `@import` ordering findings where strict parsers reject invalid placement, double-dot selector recovery, invalid media query list recovery, dynamic property name recovery, and invalid font-family punctuation recovery. These keep known classes from crowding out new syntax findings while leaving ordinary function or at-rule rejection fingerprints exact.
